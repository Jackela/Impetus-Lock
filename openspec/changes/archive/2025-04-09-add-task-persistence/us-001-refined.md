# US-001: 任务本地持久化 (精简版)

## 原始需求

**US-001**: 作为用户，我希望我的任务列表在刷新页面后仍然存在

> 当前系统所有任务数据仅存储在内存中，用户刷新页面后会丢失所有工作。这破坏了写作工具的核心价值主张。

---

## PO 详情

### 用户故事原文

**作为** 一个使用 Impetus Lock 进行写作的用户  
**我希望** 我的任务在刷新页面后仍然存在  
**从而** 我可以信任系统保存我的工作，建立持续的写作习惯

### 验收标准 (AC)

1. **AC1**: 用户创建的任务在页面刷新后仍然可见
2. **AC2**: 任务内容（包括锁定标记）被完整保留
3. **AC3**: 用户可以在任务列表中看到所有已保存的任务
4. **AC4**: 用户可以点击任务继续编辑
5. **AC5**: 删除操作在刷新后仍然生效（被删除的任务不再出现）

### 边界情况

| 场景 | 预期行为 |
|------|----------|
| 浏览器隐私模式 | 正常持久化（sessionStorage 不适用） |
| 存储空间不足 | 优雅降级，提示用户清理空间 |
| 数据格式升级 | 启动时检测版本，不兼容则清空重置 |
| 多标签页同时编辑 | 最后写入者获胜（无冲突解决） |
| 用户手动清除存储 | 数据丢失，回到初始状态 |

### 最简单的实现假设

- **单用户**: 无需用户认证
- **单设备**: 不支持跨设备同步
- **无冲突解决**: 最后写入者获胜
- **无版本迁移**: 数据结构变更时清空重置
- **无软删除**: 物理删除，不可恢复

## Tech Lead 评估

### 技术实现方案

#### 方案 A: localStorage 纯前端方案 (推荐)

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   React UI  │────▶│  TaskStore  │────▶│ localStorage│
│  Components │◀────│   (Hook)    │◀────│  (Browser)  │
└─────────────┘     └─────────────┘     └─────────────┘
```

- **存储**: localStorage (key: `impetus_tasks`, `impetus_current_task`)
- **序列化**: JSON.stringify/parse
- **同步**: 每次变更立即写入，启动时读取
- **数据量**: 5MB 限制足够（纯文本任务）

**优点**:
- 实现最简单（2-3 小时）
- 无需后端改动
- 无需用户认证
- 立即生效

**缺点**:
- 单设备限制
- 无跨浏览器同步
- 用户清除数据即丢失

#### 方案 B: IndexedDB 纯前端方案

- 类似方案 A，但使用 IndexedDB
- 支持更大存储空间
- 支持结构化查询
- 实现复杂度略高（+1 小时）

#### 方案 C: 后端 API + 数据库方案

- 需要用户认证系统
- 需要后端 CRUD API
- 需要数据库 schema
- 工作量：2-3 周

### 推荐方案

**方案 A: localStorage 纯前端方案**

**理由**:
1. **符合 MVP 原则**: Sprint 0 目标是一周内可交付
2. **满足核心需求**: 解决"刷新丢失"问题
3. **可演进**: 后续可无缝迁移到后端方案
4. **无依赖**: 不阻塞其他功能开发

### 预估工作量

| 任务 | 时间 |
|------|------|
| 创建 useTaskStorage hook | 1h |
| 修改现有 task 状态管理 | 1h |
| 添加数据序列化/反序列化 | 0.5h |
| 编写单元测试 | 1h |
| 手动验证 | 0.5h |
| **总计** | **4h** |

### 风险点

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| localStorage 被禁用 | 低 | 高 | 检测并提示用户启用 |
| 存储空间超限 | 低 | 中 | 限制任务数量/大小，超限提示 |
| 数据结构变更 | 中 | 低 | 添加版本号，不兼容时重置 |
| 性能问题（大任务） | 低 | 低 | 延迟序列化，防抖写入 |

## 关键问答

### Tech Lead 回答: 最简实现是什么？

> **最简实现**是在现有 React 状态管理基础上添加一个 `useTaskStorage` hook：
> 
> 1. 应用启动时从 localStorage 读取任务列表
> 2. 任务增删改时同步更新 localStorage
> 3. 使用 JSON 序列化，无需复杂 schema
> 4. 不改动任何后端代码
> 5. 不添加用户认证
> 
> **代码量**: 约 50 行 hook + 20 行类型定义

### PO 回答: 不做这个功能，用户还能用吗？

> **不能**。没有持久化，Impetus Lock 只是一个"玩具"而非"工具"。
> 
> 用户场景：
> - 用户写了 1000 字，不小心刷新页面 -> **全部丢失**
> - 用户关闭浏览器明天继续 -> **无法继续**
> - 用户想查看之前的任务 -> **不存在**
> 
> **结论**: 这是 P0 需求，阻塞 MVP 发布。

## 精简需求 (最终版)

### 范围

**IN 范围**:
- 任务列表本地持久化（localStorage）
- 任务内容持久化（包括锁定标记）
- 当前编辑任务 ID 持久化
- 数据版本检测（用于未来迁移）

**OUT 范围**:
- 用户认证
- 后端 API
- 跨设备同步
- 冲突解决
- 软删除/回收站
- 数据导入/导出

### 数据结构

```typescript
// localStorage key: impetus_tasks_v1
interface StoredTask {
  id: string;
  title: string;
  content: string;
  lockIds: string[];
  createdAt: number;
  updatedAt: number;
}

interface TaskStorage {
  version: 1;
  tasks: StoredTask[];
  currentTaskId: string | null;
}
```

### 关键行为

1. **启动时**: 读取 localStorage，解析为任务列表
2. **创建任务**: 生成 ID，添加到列表，写入 localStorage
3. **更新任务**: 修改内容，更新时间戳，写入 localStorage
4. **删除任务**: 从列表移除，写入 localStorage
5. **切换任务**: 更新 currentTaskId，写入 localStorage
6. **版本不兼容**: 清空存储，从空状态开始

## 验收标准

- [ ] AC1: 用户创建任务后刷新页面，任务仍然可见
- [ ] AC2: 任务内容（包括 lockIds）在刷新后完整保留
- [ ] AC3: 任务列表按更新时间倒序排列
- [ ] AC4: 用户点击任务可继续编辑，内容正确加载
- [ ] AC5: 删除任务后刷新，被删除任务不再出现
- [ ] AC6: localStorage 不可用时优雅降级（仅内存模式）
- [ ] AC7: 单元测试覆盖率 >= 80%
