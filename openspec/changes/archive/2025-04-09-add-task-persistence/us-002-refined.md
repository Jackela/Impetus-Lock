# US-002: 任务云端持久化与多设备同步 (精简版)

## 原始需求

**US-002**: 作为用户，我希望任务数据存储在云端，多设备同步

> US-001 已完成本地持久化（localStorage），但用户仍受限于单设备。云端同步是释放多设备写作体验的关键。

---

## Step 1: PO 编写用户故事详情

### 用户故事原文

**作为** 一个使用 Impetus Lock 进行写作的用户  
**我希望** 我的任务数据存储在云端并能在多设备间同步  
**从而** 我可以在电脑上开始写作，在手机上继续，无需手动传输文件

### 验收标准 (AC)

1. **AC1**: 用户在一台设备上创建的任务，可以在另一台设备上查看和编辑
2. **AC2**: 任务内容（包括锁定标记）在所有设备间保持一致
3. **AC3**: 用户登录后可以访问自己的全部任务历史
4. **AC4**: 任务更新在一台设备上保存后，另一台设备刷新可见最新内容
5. **AC5**: 离线期间创建的草稿，联网后自动同步到云端

### 边界情况

| 场景 | 预期行为 |
|------|----------|
| 离线状态 | 允许本地编辑，联网后自动同步 |
| 多设备同时编辑同一任务 | 乐观锁冲突，提示用户刷新 |
| 网络中断后恢复 | 自动重试同步，保留本地修改 |
| 会话过期 | 提示重新登录，保留本地草稿 |
| 大数据量同步 | 分页加载，优先同步最近任务 |
| 设备时间不同步 | 以服务器时间为准 |

### 最简单的实现假设

- **单用户单会话**: 不支持同一账号多设备同时编辑同一任务
- **简单冲突解决**: 最后写入者获胜（乐观锁版本控制）
- **弱离线支持**: 离线可编辑，但冲突时可能丢失数据
- **无实时同步**: 不依赖 WebSocket，刷新时拉取最新
- **全量同步**: 首次登录下载全部任务（假设 < 1000 条）

## Step 2: Tech Lead 可行性评估

### 技术方案选项

#### 选项A: 用户认证 + PostgreSQL + REST API (推荐)

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Device A   │────▶│   FastAPI   │◀────│  Device B   │
│  (Browser)  │     │   + JWT     │     │  (Browser)  │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                    │
       └───────────────────┼────────────────────┘
                           ▼
                    ┌─────────────┐
                    │  PostgreSQL │
                    │  (tasks表)  │
                    └─────────────┘
```

**实现要点**:
- JWT Token 认证（HttpOnly Cookie）
- `user_id` 外键关联 tasks 表
- 乐观锁版本控制（已有 `version` 字段）
- 分页 API 获取任务列表

**优点**:
- 与现有后端架构一致（FastAPI + PostgreSQL）
- 数据安全（用户隔离）
- 可扩展（支持未来协作功能）
- 已有数据库连接池和错误处理

**缺点**:
- 需要实现用户认证系统（新增复杂度）
- 需要数据库 migration 添加 user_id
- 工作量较大（约 1-2 周）

**工作量**: 2 周（全职开发）

---

#### 选项B: 匿名用户 + localStorage 同步令牌

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Device A   │────▶│   Sync      │◀────│  Device B   │
│  (Browser)  │     │   Server    │     │  (Browser)  │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                    │
       └──── sync_token ───┴──── sync_token ────┘
              (localStorage)      (localStorage)
```

**实现要点**:
- 无需密码，生成随机 `sync_token` 作为身份标识
- 用户手动输入 sync_token 在新设备上同步
- 可选：QR 码扫描传递 token

**优点**:
- 无需用户注册/登录 UI
- 实现简单（无需密码哈希、邮件验证等）
- 隐私友好（无需邮箱/手机号）

**缺点**:
- Token 丢失 = 数据丢失（无找回机制）
- 安全风险（token 泄露 = 数据泄露）
- 用户体验差（需手动传递 token）
- 不符合常规用户心智模型

**工作量**: 1 周

---

#### 选项C: 仅本地存储（延后云端功能）

**实现要点**:
- 保持 US-001 的 localStorage 方案
- 添加数据导出/导入功能（JSON 文件）
- 用户手动通过文件传输同步

**优点**:
- 实现最简单（2-3 天）
- 零后端改动
- 零运维成本

**缺点**:
- 用户体验差（手动文件传输）
- 无法真正做到"无缝同步"
- 与 US-002 原始需求有差距

**工作量**: 2-3 天

---

### 推荐方案

**选项A: 用户认证 + PostgreSQL + REST API**

**理由**:
1. **长期价值**: 用户认证是后续所有功能的基础（协作、分享、AI 个性化）
2. **技术债务**: 选项 B/C 都是临时方案，最终仍需迁移到 A
3. **用户体验**: 符合用户心智模型（注册/登录/同步）
4. **已有基础**: 后端已有 Task API 和数据库，只需添加用户层

**关键决策**:
- 使用 JWT + HttpOnly Cookie（而非 localStorage 存 token）
- 使用 bcrypt 密码哈希
- 添加 `user_id` 到 tasks 表，建立外键关系
- 复用现有乐观锁机制处理冲突

## Step 3: 关键问题回答

### Tech Lead: 最简实现是什么？

> **最简实现**是在现有后端基础上添加用户层：
>
> 1. **数据库**: 添加 `users` 表，`tasks` 表添加 `user_id` 外键
> 2. **认证**: JWT 登录/注册 API（3 个端点）
> 3. **API 改造**: 现有 Task API 添加 `user_id` 过滤
> 4. **前端**: 登录页面 + API 请求自动带 token
> 5. **离线**: 先不做复杂队列，离线时提示用户
>
> **代码量估算**:
> - 后端: ~300 行（认证 + API 改造）
> - 前端: ~200 行（登录 UI + API 集成）
> - 测试: ~200 行
>
> **最简版本工作量**: 1 周（不含复杂离线支持）

### PO: 不做这个功能，用户还能用吗？

> **能用，但有明显限制**。
>
> 用户场景：
> - 单设备写作 -> **完全可用**（US-001 已满足）
> - 办公室电脑开始，地铁上手机继续 -> **不可用**
> - 换电脑后访问历史任务 -> **不可用**
>
> **商业价值评估**:
> - US-001 解决"数据不丢失"问题（P0）
> - US-002 解决"随时随地访问"问题（P1）
> - 对于严肃写作工具，多设备同步是**基础竞争力**
>
> **结论**: P1 需求，不阻塞 MVP，但应在发布后 2-4 周内实现。

## Step 4: 精简需求 (最终版)

### 范围

**IN 范围 (MVP)**:
- 用户注册/登录（邮箱 + 密码）
- JWT 认证（HttpOnly Cookie）
- 任务数据按用户隔离
- 多设备登录访问同一任务列表
- 乐观锁冲突检测（提示刷新）
- 会话过期处理（跳转登录页）

**OUT 范围 (后续迭代)**:
- 社交登录（Google/GitHub）
- 邮箱验证
- 密码找回
- 实时同步（WebSocket）
- 复杂离线队列（自动重试）
- 团队协作/分享
- 数据导出

### 数据结构

```python
# users 表 (新增)
class UserModel:
    id: UUID          # 主键
    email: str        # 唯一
    password_hash: str # bcrypt
    created_at: datetime
    updated_at: datetime

# tasks 表 (修改)
class TaskModel:
    id: UUID
    user_id: UUID     # 新增：外键 -> users.id
    content: str
    lock_ids: list[str]
    version: int      # 乐观锁
    created_at: datetime
    updated_at: datetime
```

### API 变更

```python
# 新增认证端点
POST /api/v1/auth/register    # 注册
POST /api/v1/auth/login       # 登录
POST /api/v1/auth/logout      # 登出

# 现有 Task 端点改造（添加认证）
GET    /api/v1/tasks          # 只返回当前用户任务
POST   /api/v1/tasks          # 自动设置 user_id
GET    /api/v1/tasks/{id}     # 检查任务归属
PUT    /api/v1/tasks/{id}     # 检查任务归属
DELETE /api/v1/tasks/{id}     # 检查任务归属
```

### 关键行为

1. **注册**: 邮箱 + 密码 -> 创建用户 -> 自动登录
2. **登录**: 验证密码 -> 设置 JWT Cookie -> 跳转任务列表
3. **API 请求**: 自动携带 Cookie -> 后端验证 JWT -> 提取 user_id
4. **任务查询**: 自动过滤 `WHERE user_id = current_user_id`
5. **冲突处理**: 版本不匹配 -> 409 错误 -> 前端提示刷新
6. **会话过期**: 401 错误 -> 跳转登录页 -> 保留本地草稿
