# GitHub 开发范式

迭代 Issue 记录下一阶段要做什么，OpenSpec 描述要改变的行为，测试与评审为每个交付结果提供可回查的证据。

## 一手资料观察

| 来源                                            | 可借鉴的做法                                                                                                                                       |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| [VS Code 2026 年 2 月迭代 Issue](SOURCES.md#e1) | 在一个 Issue 汇总迭代时间、收尾日期和按领域组织的目标，链接子任务或查询、列出负责人，标记进行中、阻塞及额外目标。该 Issue 明示其计划结构正在试验。 |
| [Cline Bench](SOURCES.md#e2)                    | 用真实开源工程问题组织评测。任务包提供给代理的说明、初始环境、参考解法和独立验证测试，可在同一基线重放。其结果适用于所评任务与环境。               |
| [OpenSpec](SOURCES.md#e3)                       | 用 Markdown 的需求与场景记录变更，由提案和任务清单衔接实现与归档，保留现行规格的可追溯性。                                                         |
| [Karpathy 的 LLM Wiki](SOURCES.md#e4)           | 维护彼此链接的 Markdown 知识页，把源文件原样保留，用维护约定指导收录和纠错。适合积累反复要查的设计、平台与工程资料。                               |

## 在 Impetus Lock 中怎么用

- 路线图确定阶段目标。拆任务时可以让一个迭代 Issue 指向相关问题、负责人和验收证据。需求和优先顺序回查项目文件。 [路线图](../ROADMAP.md)
- 新能力、公开接口、架构和依赖变更按仓库 OpenSpec 审批流程推进。恢复既定行为的修复先复现失败。PR 写明用户可见影响、关联 Issue 或规格、基线与结果、实际命令和仍待验证的环境。 [OpenSpec 工作约定](../openspec/AGENTS.md) · [仓库约定](../AGENTS.md) · [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)
- 要复查写作功能时，可以借鉴 Cline Bench，把脱敏输入、固定仓库提交、预期结果和可重放检查放在一起。例如尝试用普通编辑删除锁句，检查正文和锁的标识仍然保留。具体预期见对应规格，交付检查按现有门禁执行。 [锁删除拒绝规格](../openspec/specs/lock-rejection-feedback/spec.md) · [开发指南](../DEVELOPMENT.md) · [CI 工作流](../.github/workflows/ci.yml)

以上案例提供组织资料与验证的参考。模型表现、项目 CI 和平台上线分别按相应结果记录，OpenSpec 变更、合并和发布仍按项目的审批约定执行。 [仓库约定](../AGENTS.md)
